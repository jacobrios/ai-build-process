# Rule lineage

Append-only record of why each user-level rule exists and what produced it. Organized to mirror `~/.claude/CLAUDE.md`'s sections so a rule and its story are findable from each other. The rules file is operative and wins where the two disagree; this file exists so the rules file does not have to carry its own history.

How to extend: when a rule is born or amended, the rule gets a short dated marker in CLAUDE.md and the narrative lands here, in the matching section, the same session. Nothing here is ever rewritten; corrections are dated annotations.

Created 31 July 2026, during the length pass that followed the rules consolidation (see `2026-07-31-rules-consolidation.md`). The initial entries below reconstruct lineage that previously lived inline in CLAUDE.md; the consolidation record holds the full audit reasoning behind the 31 July changes and is not duplicated here, only summarized where a rule needs its story to stand alone.

This file is the living home for rule reasoning and lineage going forward, and it inherits from the consolidation record rather than competing with it: where the two describe the same decision, the consolidation record is the original account, sealed to its date, and this file carries anything learned since.

## The boundary guard learns to read redirection (9 September 2026)

`repo-boundary.mjs` now treats `> path`, `>> path`, `2> path`, `&> path` and `tee path` as the writes they are, resolved and fenced exactly as `cp` destinations already were. 27 new cases in its test file (14 must-still-work, 13 must-block), 124 total, and eight sabotages each turned tests red.

Why it stopped being an accepted gap. The hook's own header had said macOS privacy settings backstopped redirection; they gate Documents, Desktop and Downloads, not `~/code`, so nothing did. And the harness now steers sessions in auto mode to prefer Bash over the Write tool for file changes ("make file changes with sed, heredocs, or short scripts"), an instruction this session received verbatim and a public Reddit thread noticed the same week. That inverted the guard: the fenced path became the one agents avoid, and heredocs became the way files get written. A worktree session wrote into the main checkout this way on 31 August and was caught only when its cleanup `rm` tripped the guard on the way out.

Three edges, all found by tests or by the guard itself rather than by reading, which is the pattern this file keeps recording. The first version matched operators only at the start of a token, so `echo x>path` passed. The second scanned tokens after the tokenizer had already stripped quotes, so it could not tell `echo "a>b"` (text) from a quoted path after a real operator (a write); the check now scans the raw segment tracking quote state. The third was found by the guard blocking this very entry: the lineage text contained a redirection example inside a heredoc, and the guard read prose as a command. Heredoc bodies are now dropped before scanning unless a shell (`bash`, `sh`, `eval`, `source`) receives them, in which case they are commands and stay scanned; the line opening the heredoc is always kept, so its own target is still fenced.

And one of the new tests could not fail: its `$name` was JSON-escaped as a backslash-dollar, invalid JSON, so the hook failed open and the test passed for the wrong reason. Found by sabotage, fixed in the test. Same lesson as suite-lock, one file over.

## The heartbeat reviewed, and what it actually reclaims (4 September 2026)

An independent review of the heartbeat returned two criticals and four smaller findings. All six were real, and the first one lands on the design rather than the comments.

**The heartbeat proves the event loop is turning, not that the run is working.** A beat is a `setInterval` on the vitest main process, which stops only if that process is killed, stopped, or blocked inside a synchronous call. Every ordinary way a run wedges leaves that loop turning: an await that never settles, a hung globalSetup or teardown (vitest applies no timeout to either), a database disconnect that never returns, a blocked pool worker. This repo even contains an instance, since `run-tests-unless-docs.test.ts` calls spawnSync with no timeout, blocking that worker's thread outright while the main process beats along. So the honest guarantee is "reclaimed when the holder is gone, or when its main loop has been blocked for two minutes", which for an orchestrator is only marginally stronger than the liveness check it replaced. The header now says that, and names the wedged-worker case as uncovered.

**And the incident it was designed against was never diagnosed.** The 308-minute holder was called hung on the strength of `ps` showing it idle, which is equally consistent with a healthy event loop. The reporting session did not establish what that process was doing, and the applying session designed a mechanism against it anyway. Both halves are recorded because the failure is the same one this repo's own notes warn about, and knowing which of us made it matters less than the next session knowing it was made. If it recurs: diagnose first, get a stack, find out whether the main loop turns and whether a worker is blocked. Do not tune the threshold at it.

**A bug the heartbeat introduced, and the sharpest finding of the day.** The beat used a plain `writeFileSync`, which truncates before writing, so the lock file is momentarily zero bytes. A waiter polling at 250ms reads it, fails to parse, calls it abandoned, and takes the lock from a live healthy holder: two suites on one database, silently, which is precisely the incident this file exists to prevent. It arrived with the heartbeat, because v1 and v2 wrote the file once and never rewrote it. Measured with two real processes: 1739 unreadable reads in 27839 with the plain write, zero in 76466 after switching to write-temp-then-rename.

**Silence was measured on the wall clock.** Close a laptop mid-run with a second run waiting and it wakes to a beat hours old, held by a run that is fine, and steals. No threshold fixes it because the measured quantity is wrong. A holder that looks silent now gets a second look before its lock is taken, since a live holder beats again inside that window and a stuck one does not. The reviewer was told not to soften anything on account of a planned mitigation, which is why this was reported as a live defect rather than a documented one.

Three smaller fixes, each a hole in the tests rather than the code, which is the pattern worth noting. A throw after the lock was taken fell into the contended branch and made a run wait five minutes on its own pid. A nested run against a different project deleted its parent's marker instead of restoring it, so a further nested run would deadlock on the parent's own lock: the v1 bug by a side door, and the test that walked that exact path asserted nothing about the marker afterwards. And the legacy-lock fallback had only its steal direction tested, so removing it entirely would have left the suite green while every pre-heartbeat lock was stolen from a healthy holder.

The test file also raced itself. Its fixture path was fixed under `/tmp`, shared by every checkout, while two worktrees are explicitly not serialized by this lock, so one run's cleanup could fail another run on an innocent assertion. Unreproducible red naming the wrong file, manufactured by the tests of the machine built to eliminate exactly that. Keyed per process now.

Confirmed clean by the same review, and worth recording because it is what the last three passes were for: all tests can fail, every injected clock advances, no frozen-clock hang remains, and all nineteen acquire calls pass an explicit env with none falling back to ambient state.

## The lock learns to tell stuck from working (4 September 2026)

Two more findings from the adopting session, and a product ruling from Jacob that turned the second from a note into work.

**Finding one: a test that hung rather than failed, and had never run.** Four tests took the default `env`, so they read whatever ambient state the process held. The session's stated mechanism was wrong, and checking rather than accepting it mattered: a project's globalSetup holds a lock keyed to the project root, whose path cannot equal the test root's, so the re-entrancy short-circuit could not have fired. Reproducing the adopted condition confirmed all four still passed. But reproducing the shipped test's exact parameters found something worse than the diagnosis. `now` was frozen while `sleep` only yielded a microtask, so elapsed time never advanced, the loop never timed out, and timers were starved: the test could not even be killed by a five-second guard. It hung rather than failed, everywhere, including here. It had simply never been run, which is precisely what the provenance work exists to surface, and the file it was testing is the one whose provenance entry is still unwritten.

Both fixed. Every test now injects its own `env` and advances its clock, with a header saying why each is required, since the failure mode of neither is a red result.

**Finding two: liveness alone cannot tell a stuck run from a working one.** The overnight suite held the lock for 308 minutes, alive and idle, confirmed with ps, and blocked every run after it. The previous version self-healed after ten minutes; the one that replaced it does not, so the real cost was never the recycled pid the header named, it was that a hung run stops everything until a human notices.

Jacob's ruling, which settled the design rather than leaving it to judgment: the fix must take the human out of the loop, and neither reverting nor documenting honestly was sufficient any more. He does not want to be a gate on code execution, and he does not want the misleading red suites back either.

So a holder now proves it is working rather than merely existing. It touches its lock file every five seconds, and a lock is stale when its holder is gone or has been silent for two minutes. Three states, all resolving unattended: alive and beating is running so wait, alive and long silent is stuck so steal, gone is gone. Both earlier versions collapsed a pair of those, and each collapse had its own incident: age-based stealing treated a healthy watcher as abandoned, and liveness alone treated a wedged run as healthy.

The numbers are argued from measurements rather than chosen round, on the session's own point that the ten minutes just removed was the same class of number. The guarded suite runs 71 to 84 seconds; five-second beats make two minutes twenty-four missed beats, so a wrongly stolen lock needs a two-minute event-loop stall inside a run whose whole length is under ninety seconds. Two minutes also sits well inside the 300-second wait, so a stuck lock is reclaimed rather than timing the waiter out. Stated as silence rather than age deliberately: age varies per project, silence does not.

Verified by mutation twice over, and the second attempt is the one worth recording. Disabling the silence check turned the 308-minute case red. Disabling the heartbeat write turned nothing red, because the assertion said `beat >= previous` and an unchanged beat satisfies that. Tightened to an exact value, the sabotage turned red properly. A test that cannot fail is not evidence, and this one could not, briefly, in the file built to stop exactly that.

## Review of suite-lock, and the bar for proof (4 September 2026)

The adopting session's independent review found four things in the template, and it was right about all four. Recorded because three of them are the same failure wearing different clothes.

**A reachable silent hang, the one real bug.** `acquire` assumed the only reason an exclusive create can fail is that the file exists. On any other failure (read-only lock directory, disk full, EACCES, EMFILE) the holder read as null, null counted as stale, the remove was a no-op, and the loop re-entered with no sleep and no elapsed check, because the timeout test sat inside the non-stale branch. A tight spin at full CPU, the suite never starting, and the 300-second guard never firing: a silent permanent hang inside the file whose entire job is making failures legible. Fixed both ways the review named, gating the steal on EEXIST and hoisting the elapsed check above the stale branch. The path cannot be provoked from a normal filesystem, so the write is now injectable and a test forces EROFS.

**The header overclaimed the guarantee, in the shape of the original incident.** It said one suite per checkout. What this delivers is one lock-TAKING suite per checkout: a nested run skips the lock by design, and in interplanetary-groups the nested `vitest related` reaches a route test that creates users, groups and events through Prisma while the parent suite runs. Two processes, one database, on every full-suite run. That predates the lock and is not worsened by it, but a comment claiming a hole is closed when it is open is worse than the hole, and it is exactly the misdirection that let the first version look finished.

**The re-entrancy comment named the wrong mechanism.** It credited plain parent-to-child environment inheritance. The reviewer read vitest's own code: global setup runs in the main process, the nested spawn happens in a pool worker, and the worker's environment is rebuilt from `process.env` after global setup has run. It works by that ordering, not by spawn inheritance, so a future vitest that snapshots worker environments earlier brings the deadlock back. Recorded as reported rather than independently confirmed here, with the symptom named.

**Watch mode silently defeated the lock.** A lock older than ten minutes was stolen even from a live holder, on the reasoning that a stuck lock nobody can clear is worse than a rare collision. But `vitest --watch` holds the lock for as long as the watcher runs, so after ten minutes every other run stole it and two suites were back on one database with no symptom at all. A live holder is now never stale; abandonment is decided by liveness alone. The cost is a recycled pid leaving a lock nobody owns, whose failure is a run that waits and throws a message naming the wait. That is legible, where what it replaces failed silently in the direction of no protection. Watch mode holding the lock is now documented rather than surprising.

**And the bar for proof moved, on the same session's argument.** It declined to record suite-lock's provenance entry even though the stated bar was met (1742 passed across 147 files, twelve suite-lock tests, zero failures), because the change sat on an unmerged branch awaiting review and Jacob's merge. If review reshaped the file or he rejected it, provenance would assert a proof for a version the project does not contain: a confident claim from a green run rather than a landed state, which is the failure the file exists to prevent, one level up. The bar is now "green in a real project's suite, on code that has landed on that project's main branch," and `record-safety-net-proof.mjs` checks it with git rather than asking. It refuses the real unmerged case, allows a file that is on main, and fails open with a note when it cannot locate the project, since a tool that refuses to run in an unfamiliar layout gets worked around.

It also declined on permissions, correctly: writing to `~/.claude/templates/` is outside its project, and my telling it Jacob had authorized the build did not extend to authorizing its write. It routed the ask to him instead of treating a peer's account as his permission.

## Proven is not the same as adopted (4 September 2026)

Raised by the session adopting suite-lock, in the same message that confirmed the deadlock fix: the drift checker could tell Jacob a template file was missing, and nothing could tell anyone it had never been executed against a real project. Those are different states and only the second is evidence. It deliberately proposed no mechanism. Jacob, on his way to bed, called it engineering-shaped and authorized building it that night.

The design is one file and one inversion. `provenance.json` in the template records which files have actually run, and the default is unproven, so a file absent from it is reported as never having run rather than passing silently. Silence now means not-yet-trusted. The bar is deliberately narrow: a file is proven when its own tests ran green inside a real project's suite, not when it was copied in and not when someone read it and approved.

Two report cases, and the second is the one worth the work. A missing file now says it is unproven rather than merely unadopted. And a file that is adopted, byte-identical to the template, and proven nowhere gets its own report, because that case is invisible from every other angle: nothing else in the checker has anything to say about a file that matches.

The five existing template files were backfilled, and marked `backfilled: true` because that is what they are. Writing confident entries into an evidence file would be exactly the failure the file exists to prevent, so each says what is actually checkable now (present in interplanetary-groups with a test sibling, last touched on a date from git) rather than claiming someone watched them pass. `project-root.mjs` has no tests of its own anywhere and is recorded as proven only indirectly, since both hook test files import it.

Verification, since this hook runs at every session start and a mistake would be expensive. The 39 existing tests were green before the change and are green after; seven new ones bring it to 46. Both new checks were sabotaged one at a time: treating every file as proven turned four red, never reporting an unproven in-use file turned three red, and restoring turned all 46 green. The hook was then run against both real projects rather than fixtures: interplanetary-groups correctly reports suite-lock as missing and never run, and b1-coach correctly reports its existing deliberate-difference acceptance as expired, because the template moved when the deadlock was fixed.

## The suite-collision incident and `suite-lock` (3 September 2026)

A subagent in interplanetary-groups was running `npm test` as its own verification at the moment `full-suite-on-subagent-stop.mjs` fired and ran the suite too. That project has one dev-test database, so the two runs contended for connections until a Prisma transaction could not start and the suite went red naming `invite-token.test.ts`, a file nobody had touched. Run alone seconds later it was 1704 of 1704 across 146 files. Reported by two sessions independently.

What made it worth machinery rather than a documented habit: the failure names innocent code. Whoever reads that red goes and debugs invite tokens, and Jacob cannot tell that report from a real defect, which is the exact failure class the safety nets exist to prevent. The already-recorded habit (re-run a red suite alone before believing it) is a fine backstop and a poor primary.

Four options were on the table. A retry on the contention signature was rejected hardest: it is the same move as re-running a test until it passes, it turns a genuine intermittent failure into silence, and a flake had just cost a session. A database per run cures the cause but is far larger than the problem, and the project already has its own queued database item. Doing nothing fails on the misleading-name argument above. So: a lock.

The design decision that matters is where the lock lives, and the obvious answer is wrong. A lock only works if every party takes it, and the two colliding parties were the hook's run and an agent's own typed `npm test`. A lock inside the stop hook covers the first and misses the second, which is the case that actually happened. `suite-lock.mjs` is therefore a vitest `globalSetup`, not a hook: vitest reads its config at the start of every invocation, so it catches every run whoever started it. Two things fall out that the hook version could not offer. It protects a session that is already running, because a config is read per invocation while a hook is loaded at session start. And it adds a file rather than editing one, so neither existing hook drifts.

It waits for an in-flight run and then runs, rather than skipping and trusting. The session that reported this asked directly whether trusting weakens the gate, and it does: the other run may have started before the last edit, so its green does not cover the current tree. Waiting costs one extra suite of background time, which the 1 September measurement showed costs Jacob nothing, since active time is one to two hours against wall clock of five to eighty. On timeout it throws with a message naming the wait rather than proceeding, because proceeding would recreate the misleading red it exists to prevent.

Evidence, since the template has no package.json and its `.test.ts` files can only run inside a project. Two real node processes raced for one lock: the second waited 1516ms for the first, which released at 1503ms. The exclusive-create flag was then removed and the race rerun, and both processes acquired at once, reproducing the collision, so the mechanism is provably load-bearing rather than incidental. Nine logic assertions were run in plain node covering stale holders, dead holders, unreadable locks, the waiting path, the timeout message, and release refusing to remove a lock someone else has taken over. The `.test.ts` ships alongside for whichever project adopts it and can actually run vitest.

*Postscript, same day.* `suite-lock` is the first file in that template that is not a hook, and a globalSetup copied without being wired does nothing while looking installed. The startup checklist's copy-the-safety-nets bullet now says to check the README for where each file is wired and confirm it runs. Drift needs no such help: it discovers every top-level `.mjs` in the template rather than reading a manifest, so it flagged the new file with nothing to register.

*Postscript, 3 September 2026: the first version deadlocked on contact.* Adopting it into interplanetary-groups hung that suite. One test there, `run-tests-unless-docs.test.ts`, deliberately spawns a real nested `vitest related` in the same checkout, as the only proof that the per-edit gate selects what it claims to. The child tried to take a lock its own parent held, waited the full 300 seconds, and failed the parent's assertion: 1704 of 1704 before, 1711 passed and one failed after. Parent waiting on child, child waiting on parent.

The fix is re-entrancy. A run that takes the lock records the lock path in an environment variable; a child inherits it, recognizes this project's own path, and skips acquiring rather than waiting. Spawned processes inherit the environment by default, so no call site changed. Keying on the path rather than a bare flag is load-bearing: a nested run against a different project still locks that one normally. Verified by mutation rather than by a green run, since a green run proves nothing here: with the fix a nested child acquired in 1ms, and with the re-entrancy line disabled the same child waited out its timeout and failed, reproducing the deadlock. Two unrelated processes still serialize, checked in the same pass so the fix could not have been bought by disabling the lock.

The honest lesson is about the first version, not the second: it was written, tested against invented cases, and never run against the suite it was written for. Every assertion it passed was one I had thought of. The case that broke it was one the real project already contained, and adoption found it in minutes. Worth remembering the next time template code looks finished because its own tests are green.

*Annotation, later the same day.* The 1704 figure above is the baseline as it stood during the incident. It moved to 1730 across 146 files when the horizon slice merged that night, measured on main by the adopting session rather than copied from a record. Anyone re-verifying these numbers should expect the newer one.

Known limitation, left alone deliberately: the lock keys on the resolved working directory, so it serializes runs within one checkout and not two git worktrees sharing one dev-test database. Closing that means keying on the database instead, which trades this failure for a worse one, a stale lock in an abandoned worktree blocking every other checkout.

Scope note: b1-coach has no database and cannot hit this, so it should record a deliberate difference rather than adopt. The template is still the right home, because a project-only fix means the next database project starts with the bug back, and the startup checklist already copies the template into anything new.

## The shared-checkout incident and `branch-cut-guard` (1 September 2026)

A session ran `git checkout -b fix-1password-diagnosis` in the shared main checkout of interplanetary-groups while another session had work in flight there. The checkout had moved to that session's feature branch, so the new branch was cut from its tip and PR #112 carried 32 commits of an unmerged feature under a title about 1Password. Had it merged, the feature would have shipped unreviewed, past the gate that is not supposed to degrade. The same commit also swept in the other session's uncommitted work. Cleaned up by the session that caught it before Jacob was asked to merge.

The relayed report said the cause was `git add -A`, and that was wrong. Messaging the session that did it produced the correction, and `git show --stat beff46d` confirmed it independently: two files, `CLAUDE.md` and `docs/build-notes.md`, staged by explicit named paths. Both sessions were editing those same two files, so naming the paths correctly still swept the other session's lines. This matters because a hook refusing `git add -A` was about to be written on the strength of that report and would have prevented nothing, while leaving the real collision available. Two agent reports disagreed; verifying rather than choosing is what settled it.

What the session actually did, in its own account: it checked the checkout hours earlier, saw a clean main, and carried that observation forward as current state without revalidating. Worse, and it volunteered this rather than being asked, it already knew the checkout had moved and had said so out loud earlier in the same conversation, reasoning correctly that switching branches would disturb the other session, and then branched there anyway. Not an information gap; a failure to connect known context to its own next action. That is what decided rule-versus-hook: prose cannot close a gap between knowing something and acting on it, and the rule it needed already existed ("start every new slice from a current main"), unread rather than disbelieved.

So both were done. The rule gained the freshness requirement (check at the moment you cut, never carry an earlier look forward) and the dirty-tree stop. `~/.claude/hooks/branch-cut-guard.mjs` blocks `git checkout -b` and `git switch -c` when HEAD is not main or the tree is dirty, exits 2 so the agent hears it, and deliberately leaves `git checkout <existing-branch>` alone (the fix-an-open-PR-in-place case) and `git worktree add` alone (worktrees caused no incidents and are the sanctioned route). Eleven tests, and both checks were sabotaged one at a time to prove they were load-bearing: disabling the branch check turned two tests red, disabling the dirty check turned one red, restoring turned all green.

The structural finding, which outlives the incident: the definition of done requires every slice to update the project's CLAUDE.md current-state section and its decision record. Those are exactly the two files that collided. Any two concurrent sessions therefore contend for them by design, guaranteed by the rules rather than by bad luck. The worktree rule is what keeps that from mattering, and it held perfectly here: the two sessions working in worktrees that day caused no problems at all, and only the shared checkout did. The reason the rule did not fire is that a session doing a quick fix never classifies itself as "concurrent work" and cannot see other sessions; a dirty tree is the observable proxy, which is why the amendment is written around that rather than around intent.

Residual gap, recorded rather than solved: the guard fires on branch creation only. A session already on a branch in a shared checkout can still stage a file another session is editing. The dirty-tree check would have to move to `git add` or `git commit` to close that, which risks false positives on a session's own legitimate work in progress.

## Before you build

**The design-gate exception (amended 31 July 2026).** The original wording was "a genuinely trivial change (a one-line copy tweak) needs a one-sentence note, not a walkthrough," a feel test. Superpowers' brainstorming skill explicitly rejects any such exception ("a todo list, a single-function utility, a config change" all go through design), which is the likely reason a small B1 Coach cold-start fix in late July 2026 felt heavier than it should have. The consolidation replaced the feel test with an objective fence plus a declared exception, accepting the residual risk of a session misjudging a change as behavior-free; the blast radius is limited because a skipped conversation never skips the PR. Dependency bumps were in the original skip list and were removed the same day, on the applying session's pushback: a session usually cannot verify that a bump changes no behavior, so listing bumps invited exactly the silent misjudgment the fence was built to prevent.

**One-shot risk absorbed into the slicing rule (31 July 2026).** "Flag one-shot risk on unproven ground" had stood alone in the engineering section since the file's first draft: if handed a large autonomous build touching integration points that don't yet exist or are untested, say so before starting and propose slicing the unproven parts out; on an established codebase with tested seams, proceed. After the length pass it was visibly derivable from the slicing rule, which already made proven ground the limit on slice size; two rules stating one principle at different moments invited confusion about whether they differed. Merged at Jacob's direction, keeping the one clause the slicing rule lacked (the same test applies when a big autonomous build arrives, since the risk won't always be visible from a product view).

**Coverage named in the slice document (added 28 August 2026).** From Matt Pocock's `tdd` skill (github.com/mattpocock/skills), which requires the seams under test to be written down and confirmed with the human before any test is written, on the grounds that nothing can be tested exhaustively so coverage is decided somewhere whether or not anyone says so. Adopted as a clause on the existing verification part of the slice document rather than as its own rule, for two reasons: a standalone confirm-first rule would add a third gate mid-execution, fighting the subagent-driven flow where the engine is told not to check in between tasks; and the slice document is already read and approved, so the decision arrives at a checkpoint that exists. Deliberately left out: the skill's other half, testing at public boundaries rather than internals, which is engineering technique Jacob would never decide and the model already does reasonably. The half worth having is "which deliberately do not," turning a silent coverage gap into a stated claim he can disagree with, the same move as the declared design-gate skip.

**Spec anatomy (added 31 July 2026).** Un-parked after the Superpowers inventory showed the plugin requires and self-reviews a spec but has nothing for fencing settled decisions, exclusions-with-homes, verification-written-before-code, or a debt forecast. It is a rule rather than a template because the plugin writes the spec and would never open a template file.

## What to surface, and when

**The execution-go gate (amended 31 July 2026).** The plugin has no plan gate: its `writing-plans` skill ends by asking "Which approach?", which is a choice of execution engine, not approval of the plan, and a casual "1" starts execution, after which the engine is instructed not to pause between tasks. On paper there was never a plan gate here either (plans are not surfaced by default), but the old fresh-session handoff was one in practice: a plan handed to a fresh session could not begin until Jacob pasted the prompt. Retiring that flow without a replacement would have deleted the gate silently. The resolution: an explicit go before any autonomous multi-task run, leaving exactly two gates in the flow, start of execution and merge, both Jacob's and both unmissable.

**Debt flagging.** The rule originally carried a second worked example ("this shortcut works now, but changing this feature after MVP will likely mean redoing this part"); trimmed in the length pass, one example carries the pattern.

**Findings arrive translated (added 3 Aug 2026).** Born the Monday after a weekend away, when a chain of three tooling micro-PRs in interplanetary-groups (#42, #43, #44) each surfaced new suggested work in its review, and Jacob named the real problem: product findings are instantly triageable, technical findings are not, so "safer to assume it's important" was the standing bias and fixing loops were eating days. The pre-AI ritual was to ask the engineering manager for a recommendation and mostly trust it; the rule makes that conversation mandatory for anything technical surfaced for a decision, from any source, not just slice reviews. Key reasoning from the discussion: a review chain never terminates on its own (every competent review finds something), so "done" is a decision, not a state the reviews reach; on a healthy team most logged findings are correctly never fixed, because a logged finding is cheap to defer and the only expensive findings are unlogged ones; and in a shop where every change costs a full PR with review and QA, "quick fix" is a fiction, which makes queue the rational default. The forced-decline clause exists because "decline is allowed" proved weaker than "decline is mandatory when nothing gets worse"; "unsure means queue, never yes" is the one clause aimed at Jacob rather than at the surfacer, countering his stated bias directly. Example whys (security risk, tiny job even for an edge case, big job for small risk) were deliberately kept out of the rule text at Jacob's call: examples in an always-loaded file act as templates and would pull future whys toward their shapes, so the texture lives here instead. A merge with the debt-flagging rule was drafted and rejected; debt-at-creation disclosure and finding-at-decision translation are two different moments, and Jacob wanted the simple "tell me when debt is created" line intact. First worked application, same day: PR #44's three open questions triaged to queue (path normalization plus making the QA script a permanent test, one combined micro-PR), decline (parsing Bash commands to close the shell bypass; real fragility cost, protecting only against a now-documented accident), and queue-low (sixteen test files sharing the 5-second remote-database timeout).

## Communication style

**The three message-shape rules (added 11 August 2026).** Born from Jacob's feedback after ten days of running the consolidated rules: messages were text-heavy, and actions or steps sometimes arrived buried in paragraphs, including a QA list delivered as prose. Inspired by the i-have-adhd skill (github.com/ayghri/i-have-adhd) but deliberately not installed: always-on communication behavior belongs in the always-loaded rules file, not an invoked skill, and several of its ten rules conflict with standing obligations (suppress-tangents against flag-debt, spot-and-say-so, and propose-next-slice; no-recap against the evidence rules). ## Engineering process and safety nets

**Turbopack refuses a symlinked dependency directory (added 1 September 2026).** The 31 August amendment prescribed symlinking `node_modules` into a worktree, and in interplanetary-groups that made the dev server unstartable: Turbopack, Next 16's default, panics with "Symlink [project]/node_modules is invalid, it points out of the filesystem root" rather than degrading. The sharpest case is the database client generated from the schema, so two branches that both change the schema must not run concurrent on symlinked dependencies. The applying session generalized it: two branches needing different packages hit the same trap by a different route, since one can import what only the other installed and its tests then pass for the wrong reason, which is precisely the failure a suite cannot catch.

## Slice and branch discipline

**One slice at a time, and the micro-PR exception (amended 31 July 2026).** The original bullet's two sentences said different things ("one slice lands fully before the next opens" is absolute; "avoid concurrent open PRs touching the same files" is about overlap) with no why stated, so a session picked blind. Naming the binding constraint as Jacob's attention settled it, and the micro-PR exception (audit item 8) falls out: a micro-PR costs almost no attention and may run concurrent when disjoint; a second full slice may not, however disjoint.

**Deploy-time obligations (added 31 July 2026).** Audit item 10. The only coverage anywhere in the stack was a single reviewer-template question about migration strategy, which is a question a reviewer may raise, not a tracked obligation.

**Propose-next-slice (added 30 July 2026; compressed 31 July 2026).** The full original rationale: this is the "recommendation, not a menu" rule applied, not an exception to it; options show the shape of the choice, the recommendation makes them useful. The reasoning can be product-shaped (what a user or the business feels next) or engineering-shaped (building this first makes the others cheaper, unblocks them, or stops something being built twice), and the sequencing argument is the one a product manager is least able to see from his own seat, so volunteering it is exactly what a good engineering manager does. The moment a slice lands is when the most is known about what should follow, and that knowledge decays fast; leaving the product manager to reconstruct it weeks later costs him the best information he will ever have. Draw candidates from what the finished slice surfaced, the project's decision record, and the debt named along the way. The choice stays his.

**Open a PR and stop, with no local-merge option (amended 31 July 2026).** Superpowers' `finishing-a-development-branch` presents a fixed four-option menu where option 1 is merge locally. The menu asks, so nothing merges without a yes, but the failure mode is a tired human typing "1" at the end of a long build, which responds to the option not being offered, not to better instructions. A local merge skips the PR and with it the QA script, the decision-record entry, and the PR body disclosures at once. The asymmetry that clinched it: option 4 (discard) requires typing the word, while option 1, the one that violates the process, requires one character; the menu protects against data loss and not process loss, which is backwards here, since a discarded branch is far easier to recover than an unreviewed merge is to undo. Whether the finishing skill honors a declared preference the way the worktree skill does was not verified; a stated rule is sufficient grounds to skip the option and say why.

## Verify and report honestly: the mobile pass (added 14 August 2026)

The rule: anything visual gets a pass on a real phone before the QA script is written.

**What produced it.** The chat-feed-boundary slice (interplanetary-groups, PR #66) was verified
thoroughly on a desktop browser: rendered comparison against the design boards, computed styles
sampled from the live DOM, hit tests, 888 passing tests. All of it correct, and all of it blind
to the finding that mattered most. The owner ran the QA on a phone over the LAN and immediately
saw that the pinned card region had squeezed the chat feed into a strip, which no desktop
viewport showed because there was enough height for both. That finding reordered the slice
queue: card-height reduction jumped ahead of the next planned polish slice.

**Why it became a rule rather than a note.** It was the second occurrence. The first was the
enlarged-device-text check during the visual-language phase, which produced the "layout grows
with content, never clips" rule for the same underlying reason: the product is a phone product,
and desktop verification is a proxy that silently passes things the real target fails. A
recurrence is the project's own threshold for writing the solution down instead of solving it
again.

**Placed in "Verify and report honestly" rather than in the PR handoff checklist**, and
deliberately: it is an obligation on the verification itself, not on the handoff. Doing it only
at handoff time would mean discovering a layout problem after the branch is finished, which is
exactly what happened here. Its position directly under the rendered-comparison rule is the
point: a rendered comparison on the wrong screen size is still not a rendered comparison.
